## 1. 比較した3つの案

| | 案1：Supabase ＋ Next.js | 案2：Firebase ＋ Web画面 | 案3：Googleフォーム ＋ スプレッドシート ＋ Apps Script |
|---|---|---|---|
| どんな仕組みか | 表形式のデータベース（名簿・チーム・入金などを表で管理）と、ログイン・写真保管が1つのサービスにまとまっている | Googleのサービス。データを「表」ではなく「文書の束」で保存する | 普段使いのGoogleフォームとスプレッドシートを組み合わせる |
| **費用（年間）** | 無料〜約3.5万円（下記4参照） | 無料〜約1万円（使った分だけ課金） | 無料 |
| **運用の難しさ** | 普段の運用は管理画面のみで完結。仕組みを直すときはエンジニアが必要 | 案1と同じくらい。ただし集計の仕組みが複雑になりやすい | 最初は簡単。ただし不具合が起きると直せる人が限られ、属人化しやすい |
| **選手を1人ずつ繰り返し入力** | ◎ 自由に作れる | ◎ 自由に作れる | ✕ フォームは「25人分の繰り返し」が苦手。25人×10項目＝250問のフォームになる |
| **写真アップロードと自動検査** | ◎ アップロードの前にスマホ上で大きさ・縦横比を検査し、日本語で理由を表示できる | ◎ 案1と同じ | △ フォームのファイル添付は**Googleアカウントへのログインが必須**で、大きさ・縦横比の検査ができない。不適合は後から目で探すしかない |
| **ZIP一括出力**（約2,000枚の写真） | ○ 事務局のパソコン上でまとめてZIPを作る方式で対応 | ○ 案1と同じ | ✕ Apps Scriptは1回6分・1ファイル約50MBまでの制限があり、2,000枚のZIPは作れない（チームごとに分ければ一部可能） |
| **権限管理**（地区は自地区のみ等） | ◎ データベースそのものに「誰がどの行を見られるか」を設定でき、画面の作りを間違えても漏れにくい | ○ 可能だが、データの持ち方と権限の設定が絡み合い、設計を間違えると漏れやすい | ✕ スプレッドシートは「シート単位・ファイル単位」でしか共有できず、地区ごとに分けるにはファイルを分けるしかない。共有設定のミスで全データが見えてしまう危険がある |
| **集計・Excel出力** | ◎ 表形式なので「地区ごとの未入金」などの集計が得意 | △ 集計用の仕組みを別に作る必要がある | ◎ スプレッドシートそのもの |
| **締切直前の同時アクセス** | ◎ 問題なし | ◎ 問題なし | △ 同時に書き込むと、まれに上書き・取りこぼしが起きる |
| **年度ごとの複製・再利用** | ◎ 「大会」単位でデータを分けて、設定を複製できる | ○ 可能 | △ ファイルを丸ごとコピーして手作業で整える |
| **変更履歴（誰が何を変えたか）** | ◎ データベースが自動で記録する仕組みを作れる | ○ 作れるが手間がかかる | △ スプレッドシートの版の履歴はあるが、「誰がどの選手の背番号を変えたか」を追うのは難しい |
| **将来の引き継ぎ** | ○ 中身はPostgreSQLという世界標準のデータベースで、他社への引っ越しも可能 | △ Google独自の仕組みで、引っ越しが難しい | △ Googleアカウントの持ち主が変わると引き継ぎが難しい |

## 2. 案3（Googleフォーム等）の限界について

案3は「すぐ始められて無料」という大きな長所がありますが、今回の要件では次の点で**要件を満たせません**。

1. **選手25人分の名簿を1人ずつ入力する画面が作れない。** フォームは1回の回答が1行になるので、名簿のような「1チームに25行」の入力には向いていません。
2. **写真の検査ができない。** 大きさ・縦横比が足りない写真も受け付けてしまい、不備の確認は事務局が1枚ずつ目で見ることになります（約2,000枚）。また、提出者全員にGoogleアカウントが必要です。
3. **地区学連ごとの閲覧制限ができない。** 個人情報（未成年を含む氏名・顔写真）を扱うのに、「自分の地区だけ見せる」がファイルの分割でしか実現できず、設定ミスによる情報漏えいの危険が大きいです。
4. **入稿用ZIPを一括で作れない。**

「申込の一部（旅行社の希望調査だけ）」のような小さな用途なら、案3は十分な選択肢です。

## 3. 推奨：案1（Supabase ＋ Next.js）

**理由**

1. **個人情報を守りやすい。** 「地区学連は自地区のチームだけ」「旅行社は手配に必要な項目だけ」という制限を、データベース自体にかけられます。画面側の作りに漏れがあっても、データは見えません。
2. **名簿・入金・提出状況の集計が得意。** 申込は「大学 → チーム → 選手」という表の形がそのまま合っています。
3. **ログイン・写真保管・データベースが1つのサービスにまとまっている。** 契約・管理するサービスが少なく、引き継ぎが楽です。
4. **招待メール方式のログインが標準で使える。** ご要望の「事務局がメールで招待」をそのまま実現できます（送信は東北学連のGmailを経由）。
5. **年度ごとに分けて複製する構造が作りやすい。**
6. **引っ越しができる。** 中身は世界標準のデータベースなので、将来ほかのサービスに移すこともできます。

**懸念点と対策**

| 懸念 | 対策 |
|---|---|
| 仕組みそのものを直すときはエンジニアが必要 | 金額・日程・画像条件・地区・口座などは**すべて管理画面で変更**できるようにし、普段の運用ではプログラムを触らない。手順書を用意する |
| 無料プランは「1週間使わないと一時停止」「自動バックアップなし」 | 受付期間（5〜11月）だけ有料プランにする（下記4） |

## 4. 費用の見込み（案1）

| 期間 | 内容 | 月額 | 期間の合計 |
|---|---|---|---|
| 開発・試験運用（〜2027年4月） | 無料プラン | 0円 | 0円 |
| 受付・大会期間（2027年5〜11月の7か月） | Supabase Pro（毎日の自動バックアップ・一時停止なし・写真100GBまで） | 約3,750円（25ドル） | 約26,000円 |
| 大会後〜削除まで | 無料プランに戻す（写真は削除・名簿のみ保管） | 0円 | 0円 |
| 画面の公開（Vercel） | 無料プラン（非営利の学生連盟としての利用） | 0円 | 0円 |
| メール送信 | 東北学連のGmail | 0円 | 0円 |
| **年間合計** | | | **約2.6万円** |

- 写真はアップロードの前にスマホ上で印刷に十分な大きさ（長辺1,600px程度）に縮小してから保存するので、64チーム分でも1〜2GB程度に収まります。
- 費用を完全に0円にしたい場合は、受付期間も無料プランで運用することも可能です（写真容量1GBまで・バックアップは手動）。おすすめはしませんが、選択肢として残します。
- Vercel（画面の公開）の無料プランは「営利目的でない利用」が条件です。全日本学連として規約上の心配がある場合は、有料プラン（月約3,000円）または同等の無料サービス（Netlify等）に切り替えます。

## 5. 使う技術の一覧（エンジニア向け）

| 役割 | 採用するもの |
|---|---|
| 画面 | Next.js（React）＋ TypeScript、スマホ対応のデザイン |
| 公開 | Vercel |
| データベース・ログイン・写真保管 | Supabase（PostgreSQL、Supabase Auth の招待機能、Storage） |
| 権限 | PostgreSQL の行レベルセキュリティ（RLS） |
| メール | Gmail のSMTP（アプリパスワード）経由 |
| PDF出力 | ブラウザ上でPDFを作成（様式Ⅰ・Ⅲ） |
| Excel出力 | ExcelJS |
| ZIP出力 | 事務局のブラウザ上でZIPを作成（サーバーの時間制限を受けない） |
| 締切リマインド | Supabase の定期実行機能（毎朝、締切が近いチームに送信） |
